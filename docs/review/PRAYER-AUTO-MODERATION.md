# Prayer screening

New prayer requests remain pending until screened by the authenticated prayer-moderate function. It sends only the shared theme, reason and display alias to the existing Alibaba Qwen provider. The app discloses this before submission. Ordinary distress and requests for support are not keyword-blocked; the prompt distinguishes them from threats and encouragement of harm, without judging denomination or doctrine.

Only an explicit certain allow with no flags can publish. A service-only SQL function binds the decision to an author and one-time claim token, rechecks pending state, account confirmation and suspensions, and sends opted-in invitations transactionally. Human approval, rejection or closure wins over an in-flight result. Flags, invalid output, quota/provider failures and absent calls leave manual review available. Reports remain unchanged. Model decisions are not infallible.

Each request gets at most one automatic attempt. A lost connection, skipped client invocation, unavailable provider or interrupted request stays pending for manual review; there is no background retry worker. Existing pending requests are not screened in bulk. Set PRAYER_AUTO_MODERATION_ENABLED=false to disable new checks. Uses the existing community_moderation AI quota. Screening flags, summary and timestamp are private audit fields, not exposed in member cards. A failed screen never turns successful creation into an error inviting duplicate submissions.

Backend migration and prayer-moderate v1 deployed. Verified live RLS and service-only execute grants; unauthenticated HTTP returns 401. Local database tests cover ownership, denied client calls, once-only notifications, holds, malformed flags, suspension, missing results and competing human review. Existing parser tests cover malformed/uncertain output. Typecheck, lint, mobile tests and web build pass.
